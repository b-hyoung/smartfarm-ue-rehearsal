# 목적 리스트업 — CFD → UE 시각화

작성 2026-09-03 · 실행자: Claude (사용자 부재 중 자율 진행)

> 상위 맥락: 스마트팜 디지털 트윈 과제의 **R3(열·유동)** → **R6(UE 통합)** 인계 구간.
> 지금은 **진짜 CFD 데이터**(OpenFOAM v2512, 900초 transient)를 UE 로 반입하는 단계.

---

## 0. 최종 목적

**언리얼에서 스마트팜 공간의 기류를 온도색으로 보고, 재배단 오브젝트 사이로
바람이 어떻게 지나가는지 눈으로 확인한다.**

기류는 실측이 비싸서 CFD 로 대체하고, 온도는 싼 센서로 검증한다 —
즉 **온도가 맞으면 기류장을 신뢰**하는 프록시 전략.

## 2. 각 목적의 구현 방침

### O3 온도 애니메이션
- `sf_viz.py` 를 프레임 루프로 확장 (`flush` → 다음 프레임 draw)
- 색 범위 **19~27℃ 전 프레임 고정** — 프레임마다 바꾸면 비교 불가
- 각 프레임 캡처 → GIF

### O4 재배단 오브젝트
- 2단 수직 재배단. 회의록 기준 "2단 수직 재배단 + 조명 + 팬 + 냉방기"
- StaticMeshActor(Cube) 조합으로 프레임+선반 구성
- ⚠ **CFD 는 빈 방 해석이라 재배단이 유동에 반영돼 있지 않다** — §3 에서 반드시 명시

### O5 기류 시각화
두 갈래로 간다. 하나가 막혀도 다른 하나가 남게.

| 방식 | 장점 | 위험 |
|---|---|---|
| **A. 파티클 이류(advection)** — CFD 속도장을 따라 입자를 직접 적분해 이동 | 실제 데이터 그대로. 파이썬만으로 완결 | 디버그 드로우라 입자 수 한계 |
| **B. Niagara + Vector Field** — 속도장을 `.fga` 로 내보내 VectorField 에셋 임포트 | 엔진 정식 파이프, 입자 수 많음 | Niagara 시스템 저작이 파이썬에 미노출일 수 있음 |

A 를 먼저 확보하고 B 를 시도한다.

## 3. 적대적 검증 체크리스트

**"그럴듯해 보이는데 틀린 것"을 찾는 게 목적.** 각 항목은 반증을 시도한다.

### V1. 좌표 정합
- [ ] UE 점군의 바운딩박스가 CSV 의 min/max 와 일치하는가 (cm 환산 포함)
- [ ] 에어컨 위치(x=4.0, y=2.0)에 실제로 냉기가 있는가 — **엉뚱한 곳이 차가우면 좌표가 뒤집힌 것**
- [ ] 좌우 대칭(B·D 지점)이 화면에서도 대칭인가

### V2. 온도 정합
- [ ] UE 에서 읽은 T 와 CSV 의 T 가 같은가 (샘플 대조)
- [ ] frame_00 이 균일 28.85℃ 인가 (냉방 전)
- [ ] 컬러맵이 전 프레임 고정인가 — **프레임마다 재조정되면 애니메이션이 거짓말**

### V3. 시간축
- [ ] 프레임 순서가 시간 순인가 (0 → 900초)
- [ ] 프레임 간 온도가 단조 감소인가 (물리적으로 그래야 함)

### V4. 기류 정합
- [ ] 속도 벡터가 천장 취출구에서 **아래로** 향하는가
- [ ] |U| 최댓값 위치가 CSV 와 일치하는가 (취출구 근처 ~1.85 m/s)
- [ ] 파티클이 벽을 뚫고 나가지 않는가

### V5. 물리 타당성 (verification)
- [ ] 질량 보존: 취출 유량 ≈ 리턴 유량
- [ ] 에너지 방향: 시간이 갈수록 방 평균 온도가 내려가는가

### V6. ⚠ 해석의 한계 — 반드시 명시
- [ ] **재배단이 CFD 에 없다** — 화면엔 오브젝트가 보이지만 유동은 빈 방 기준
- [ ] **벽 온도 29℃ 고정 가정** — 실측 미반영
- [ ] **취출 방향이 수직 아래** — 실물 4Way 는 베인이 바깥으로 뿜음 (실측에서 드러난 오류)

> V6 를 숨기면 "예쁜 거짓말"이 된다. 화면에 주석으로 띄우거나 문서에 남긴다.

## 5. O5 결과 — "나이아가라 쓴 거 맞음?" 에 대한 답

**처음엔 아니었다.** `sf_flow.py` 의 기류 표시는 `draw_debug_line` 이었다.
에디터 디버그 그림이라 PIE/빌드에 안 나오고, 파티클도 아니고, 시퀀서로 못 찍는다.

**지금은 맞다.** 경로는 이렇다.

```
data/frames/frame_14.csv        OpenFOAM 900초 결과
   ↓ src/make_fga.py            48 x 34 x 16 격자로 리샘플, cm/s 로 환산
data/fga/flow_14.fga            Fluid Grid ASCII
   ↓ unreal.VectorFieldStaticFactory
/Game/VectorFields/VF_flow_14   VectorField 에셋 (bounds 0~800, 0~570, 0~270 cm)
   ↓ User.VectorField
/Niagara/VectorFields/VectorFieldVisualizationSystem
   ↓
SF_Niagara_Flow (NiagaraActor)  파티클이 CFD 속도를 따라 이류
```

방 정렬: `FieldLocation = (400, 285, 135) cm`(방 중심),
`FieldScale = (800/563, 570/563, 270/563)`.
캡처로 바닥 D자 형상과 박스가 겹치는 것을 확인했다.

### 남은 한계 (숨기지 말 것)

- **연출이 디버그용이다.** 엔진 기본 `VectorFieldVisualizationSystem` 은 속도장을
  빨간 화살표 + 흰 경계상자로 그리는 **검사용** 에셋이다. 온도 컬러 그라디언트나
  리본 트레일 같은 연출은 들어 있지 않다.
- **파이썬으로 나이아가라 시스템을 저작할 수 없다** (`NiagaraSystemFactoryNew` 가
  `emitters_to_add` / `system_to_copy` 를 노출하지 않음 — 확인함).
  더 나은 그림을 원하면 **에디터에서 한 번** 시스템을 만들어야 한다:
  `/Niagara/VectorFields/VectorFieldParticleEmitter` 만 넣은 시스템을 만들고
  (화살표·경계상자 이미터 제외), 파티클 색을 `SampledVector` 길이 또는
  온도 텍스처에 물리면 된다. 그 뒤로는 파이썬이 `.fga` 만 갈아 끼우면 프레임 재생이 된다.
- **프레임 애니메이션은 아직 정지 상태.** `flow_00 ~ flow_14` 15개를 다 내보냈지만
  현재 레벨엔 `flow_14`(900초) 하나만 물려 있다.
- **§3 V6 의 해석 한계는 그대로다.** 재배단이 CFD 에 없고, 취출 방향이 수직 아래다.

### 곁가지로 확인한 것: UE 5.8 의 Epic MCP

사용자 말대로 5.8 에 Epic 공식 `ModelContextProtocol` 이 들어왔다(Experimental).
다만 **UE 를 MCP 서버로 만들어 우리가 만든 UFUNCTION 을 도구로 노출**하는 물건이고,
나이아가라 저작 도구가 들어 있는 게 아니라 위 한계를 풀어주지는 못한다.
자세한 건 `docs/UE-NOTES.md`.

## 6. O5 재작업 — "파티클이 뭐하러 있냐고, 장식"

사용자 지적이 맞았다. 측정해보니:

| 3초 간격 | 변한 픽셀 | 파티클 무리 무게중심 |
|---|---|---|
| 1→2 | 69,087 | (865.5, 449.5) → (866.7, 450.1) |
| 1→3 | 68,793 | → (867.0, 447.6) |

개별 파티클은 속도장을 따라 움직이지만 **무리 전체는 1~2픽셀도 안 움직인다.**
엔진 기본 `VectorFieldParticleEmitter` 는 필드를 *검사*하려고 방 한가운데 고정된 구에서
균일하게 뿌리는 물건이라, 발생 위치·형상을 못 바꾼다 (이미터 저작이 파이썬에 미노출 —
`NiagaraSystem.emitter_handles` 도 미노출인 것까지 확인).
액터를 취출구로 옮기고 `FieldIntensity` 를 10배로 올려도 구 모양 그대로였다.

### 대안: 유선을 ProceduralMesh 튜브로 굽는다

```
data/frames/frame_14.csv  +  data/traces/trace_14.csv
    v src/make_ribbons.py       궤적 각 점에 그 자리 T 를 최근접 조회로 실음
data/ribbons/ribbon_14.csv      pid, x, y, z, T, speed  (cm / 섭씨)
    v ue/sf_streamlines.py      3면 튜브 + 정점색
SF_Streamlines (ProceduralMesh) 유선 140개 · 정점 33,600 · 삼각형 66,360
```

- **색 = 그 지점의 온도** (19~27℃ 고정 램프 — `sf_viz`/`sf_animate` 와 동일)
- **굵기 = 그 지점의 속도** (얇으면 정체)
- 디버그 드로우가 아니라 **실제 지오메트리** → PIE·빌드·SceneCapture·시퀀서에 다 나온다
- 정점색을 읽는 Unlit 머티리얼 `/Game/Materials/M_SF_VertexColor` 를 파이썬으로 생성
  (`MaterialEditingLibrary.create_material_expression`)

### 이 그림이 드러낸 것

1. **급기가 수직으로 떨어진다.** 카세트 밑에서 파란 기둥이 바닥까지 곧장 내려온 뒤
   퍼지면서 하얘진다(데워진다). §3 V6 의 "취출 방향 수직 아래" 한계가 눈에 보인다.
   실물 4Way 베인은 바깥으로 뿜으므로 **이 부분은 아직 틀린 그림이다.**
2. **반원 쪽 절반이 정체다.** 유선의 92%가 y=1.0~2.0 m 띠에 몰려 있고
   **y>3.0 m 에 도달한 궤적은 0%** (12.8초 적분 기준).
   속도장 자체로도 확인된다 — y>3.0 m 평균 0.075 m/s vs y<=3.0 m 평균 0.138 m/s.
   "안 통한다"가 아니라 **절반 수준으로 느리다**가 정확한 표현.

### Niagara 는 어떻게 됐나

`SF_Niagara_Flow` 는 그대로 둔다. 빨간 화살표(속도장)는 진짜 Niagara 이고
물리적으로 의미가 있다. 다만 파티클 구와 흰 경계상자가 같이 묶여 있어 개별로 못 끈다.
이후 사용자 요청으로 `SF_Niagara_Flow` 는 삭제했다 (§7). `.fga` 파이프라인은 유지.

## 7. 화살표도 직접 만든다 — 엔진 Niagara 시각화 대체

사용자 요청: "반짝이는 파티클은 없애고, 저 빨간색이 무슨 표시인지부터".

**빨간 화살표의 정체**: 속도 벡터. 방향 = 바람 방향, 길이 = 속도 크기
(에셋 셰이더 문자열 `0.1/256.0*length(Output.SampleVectorField.SampledVector)*Particle...`).
**색은 고정 빨강이라 아무 정보가 없다.**

파티클 구만 끄는 건 불가능하다(한 시스템에 묶여 있고 이미터 저작 미노출).
그래서 화살표째 우리가 만들고 Niagara 액터는 껐다.

```
frame_14.csv → src/make_arrows.py → data/arrows/arrow_14.csv
             → ue/sf_arrows.py    → SF_Arrows (ProceduralMesh)
   화살표 363개 · 정점 3,630 · 삼각형 3,993
```

- 격자 0.55 m, 높이 3단 (0.6 / 1.4 / 2.2 m). 각 격자점은 반경 0.30 m 셀 평균
  (셀이 산재해 있어 최근접 하나만 쓰면 값이 튄다)
- **길이·색 = 속도.** 회색(정체) → 호박색(0.45 m/s). sqrt 스케일이라 느린 곳도 보인다
- ★ 유선의 온도 램프(파랑-흰-빨강)와 **다른 색 계열**을 쓴다. 한 화면에 척도가
  둘인데 계열이 비슷하면 서로 오독한다
- 글리프는 그림자를 안 던지게 했다 (`cast_shadow=False`) — 바닥이 얼룩덜룩해져서
  유선 온도색을 읽는 데 방해된다

### 지금 화면의 색 규칙 (두 가지, 서로 다름)

| 대상 | 색 | 뜻 |
|---|---|---|
| 유선 튜브 | 파랑 → 흰 → 빨강 | **온도** 19~27℃ |
| 화살표 | 회색 → 호박 | **속도** 0 ~ 0.45 m/s |

## 8. O3 애니메이션 — 완료

사용자 요청: "재배단 없이, 바람이 어떻게 지나가고 온도가 어떻게 변하는지 **바람의 색으로**".

### 바뀐 것

- **색 척도를 온도 하나로 통일.** 화살표 색도 속도(회색-호박)에서 **온도**(파랑-흰-빨강)로 바꿨다.
  속도는 이제 색이 아니라 **크기**로만 말한다 (화살표 길이 / 튜브 굵기).
  한 화면에 색 척도가 둘이면 "저 바람이 찬가 더운가"를 읽을 때마다 헷갈린다.
- **재배단 숨김.** CFD 자체가 빈 방 해석이라(§3 V6) 재배단을 빼는 편이 오히려 정직하다.
- `ue/sf_geom.py` 로 공용화. `sf_streamlines.py` / `sf_arrows.py` / `sf_bake_anim.py` 가 같이 쓴다.

### 파이프라인

```
frames + traces → src/make_ribbons.py  → data/ribbons/ribbon_NN.csv
frames          → src/make_arrows.py   → data/arrows/arrow_NN.csv
                → ue/sf_bake_anim.py   → out/anim/f_NN.png      (SceneCapture2D)
                → src/make_video.py    → out/smartfarm-flow.gif / .mp4
```

한 번의 원격 연결로 15프레임을 다 돈다. 액터는 한 번만 만들고 **메시 섹션만 갈아 끼운다.**

| 900 | **23.55** | **23.43** | 1.846 |

- frame_00 은 화살표·유선이 **0개**다. 냉방 전이라 속도가 0인 게 맞다 (오류 아님).
- 냉각이 앞 3분에 몰려 있다: 0~190초에 3.0 K, 190~900초에 2.3 K.
  시상수 τ=232초와 일치한다.
- 최대 유속은 전 프레임 1.84 m/s 로 고정 — 취출구 경계조건이니 당연하다.
  **이게 안 변하면 경계조건이 제대로 걸려 있다는 뜻**이라 점검 지표로 쓸 수 있다.

## 9. 최종 정리 — 지금 데이터 기준으로 일관되게

실측 온도계가 신뢰를 잃어(29→27℃ 가 CFD 예측 23.9℃ 와 3.1 K 차이, 센서 지연으로
설명하려면 시정수 13.6분이 필요 — 비현실적) **CFD 데이터 기준으로만** 산출물을 맞췄다.

### 화면 구성

| 요소 | 색 | 크기 | 액터 |
|---|---|---|---|
| 유선 튜브 | 온도 | 굵기 = 속도 | `SF_Streamlines` |
| 속도 화살표 | 온도 | 길이 = 속도 | `SF_Arrows` |
| A/B/C/D 기둥 | 그 높이의 온도 | — | `SF_Probes` + `SF_Probe_A~D` |

- 색 척도 하나(**온도 16.35~28.85℃**, ParaView `horz_T.gif` 와 동일)
- 화살표는 **1.1 m 한 평면 77개**. 세 층을 그리면 깊이 방향으로 겹쳐 벽처럼 보인다.
  느린 25% 는 제거 — 짧은 화살표 밭보다 **없는 것**이 정체를 더 잘 말한다.
- 재배단은 숨김. CFD 에 없는 물체를 그리면 유선이 선반을 통과하는 거짓말이 된다.

### 산출물

| | |
|---|---|
| `out/smartfarm-flow.mp4` / `.gif` | 15프레임 · 시간·범례 구움 |
| `/Game/Cinematics/SEQ_SF_Flow` | UE 시퀀스 · **재생 1초 = 실제 30초** · 32초 |
| `SF_SeqPlayer` | 레벨 재생기 (auto_play, 무한반복) — PIE 로도 재생 |
| `sh ue/frame.sh N` | 특정 프레임만 레벨에 세우기 |
| `data/probes.csv` | A/B/C/D × 3높이 × 781시각 (실측 비교 기준값) |

### 역산으로 확인한 것 (src/room_model.py)

```
CFD 곡선   T(t) = 23.44 + 5.43 exp(-t/232)   RMS 0.018 K
tau = 232초 = V/Q (0.2% 이내)
냉방부하 3,563 W = 명판 9,000 W 의 40%      -> 가능
벽 UA 641 W/K -> U = 6.4 W/m2K              -> 실내 대류 2~10 범위, 타당
```

**★ 모순**: 벽 부하가 (Tw−T) 에 비례한다면 tau 는 102초여야 하는데 실제로는 232초다.
tau 가 V/Q 와 정확히 같다는 건 벽 열유입이 **방 평균온도에 거의 반응하지 않는다**는 뜻 —
벽 근처 공기가 방 평균과 따로 논다. **이 방은 완전혼합이 아니다.**
(반원 안쪽 0.075 m/s vs 평벽 쪽 0.138 m/s)
→ 단일 온도로 이 방을 그릴 수 없다는 게 수치로 나왔다. A/B/C/D 를 따로 보는 근거.

### 남은 오류 (고치려면 재계산 필요)

1. **취출 방향 수직** — 실물 4Way 는 천장면 25°. `cases/acRoom-vane25` 준비됨(미실행, 약 6시간)
2. **재배단 미반영** — 격자부터 다시 만들어야 함
3. **벽 29℃ 고정** — 실측 미반영. 적외선 온도계로 벽면 실측이 가장 싼 개선

## 10. 시각화 최종 — "색이 안 변한다" 를 고친 과정

사용자 지적 세 번을 거쳐 고쳤다. 원인이 전부 **컬러맵과 면적**이었다.

### (1) 색칠된 면적이 없었다 → 1.1 m 온도 단면 추가

관(유선)과 화살표만으로는 색칠된 픽셀이 너무 적어서 색이 변해도 눈에 안 띈다.
`src/make_slice.py` → `data/slices/slice_NN.csv` (51x36 격자, 1,420점) →
`sf_geom.build_slice()` → `SF_Slice` (반투명 정점색 메시).

- 불투명하면 아래 유선을 가리고, 0.55 로 투명하게 하면 검은 배경이 비쳐 색이 죽는다.
  **0.82** 가 절충점.
- 1.1 m = 서 있을 때 몸통 높이. probes 기준 높이, ParaView `horz_T` 와 같은 높이.

### (2) 발산형 컬러맵의 흰 중간값이 방 평균온도와 겹쳤다

파랑–**흰색**–빨강 램프에서 흰색이 24.65℃ 였는데 방 대부분이 23~25℃ 였다.
→ 전 프레임이 흰색으로 뭉개져 **공간 차이가 안 보였다**.

가운데에도 색이 계속 바뀌는 6단 램프로 교체:

| 위치 | 색 | 온도 |
|---|---|---|
| 0.00 | 남색 | 20.4℃ |
| 0.28 | 파랑 | 22.8℃ |
| 0.46 | 청록 | 24.3℃ |
| 0.62 | 연두 | 25.7℃ |
| 0.80 | 호박 | 27.2℃ |
| 1.00 | 빨강 | 28.9℃ |

파랑을 0.20 → 0.28, 청록을 0.40 → 0.46 으로 민 이유: 900초 방 평균(23.5℃)이
램프의 36% 지점인데 처음 배치에서는 그게 청록에 걸려 "다 식었는데 파랗지 않다" 가 됐다.

### (3) 매끄러운 그라디언트는 경계가 없었다 → 0.5 K 등온 띠

`temp_color(T, quantize=0.5)`. 지도 등고선처럼 구역이 끊겨 보인다.

### 그 외

- 척도 폭: 16.35~28.85 (12.5K) → **20.4~28.9 (8.5K)**. 데이터가 실제로 도는 구간에 맞춤
- 카메라: 옆에서 보던 것을 **52° 내려다보기** 로. 수평 단면은 위에서 봐야 면적이 보인다
- 화살표를 단면 위 13 cm 로 띄움 (둘 다 1.1 m 라 묻혔다). 값은 1.1 m 것 그대로
- 화살표에 줄무늬 1개 흐름 애니 (`M_SF_ArrowAnim`) — 꼬리에서 촉으로 마루가 지나간다
- 에어컨 본체(`SF_AC_Body`)는 위에서 볼 때 가운데를 가려서 숨김. 판넬·취출구는 남김

### 검증 (렌더된 픽셀 직접 측정)

| t(s) | 화면 평균 RGB | 색 |
|---|---|---|
| 0 | (174, 21, 12) | 빨강 |
| 190 | (136, 164, 79) | 노랑 |
| 320 | (90, 156, 141) | 연두 |
| 640 | (43, 140, 163) | 파랑 |
| 900 | (35, 130, 165) | 파랑 |

시퀀스도 스크럽해서 대조했다 (t=2 → 프레임00 빨강, t=130 → 프레임02, t=320 → 프레임05,
t=640 → 프레임10 파랑). 시퀀스 표시프레임 번호 = 실제 경과 초가 정확히 맞는다.

**전체가 남색까지는 안 간다.** 급기가 16.35℃ 인데도 방 대부분은 23℃ 에서 멎는다 —
벽에서 3,563 W 가 계속 들어오기 때문(§9 역산). 그림이 그 사실을 그대로 보여준다.

## 11. 마지막 두 지적 처리 — "깜빡임 정신사납다" · "온도변화 한눈에 안 들어옴, 반짝이는 이유 찾아라" (2026-09-04)

### (1) 반짝임의 원인 — 흐름 무늬 애니메이션의 위상 잡음

화살표의 시간 기반 줄무늬 애니(`M_SF_ArrowAnim`, §10)가 범인이었다.
실시간 재생에서는 방향을 알려주지만, **프레임을 하나씩 구워 붙이는 영상에서는
캡처 시각이 제각각이라 무늬 위상이 매 프레임 랜덤**이 된다.

측정: 같은 CFD 프레임을 2초 간격으로 두 번 캡처 → **18,115픽셀이 다름.**
후반부 프레임 간 실제 온도 변화(27,792픽셀)의 65%. 신호와 잡음이 같은 자릿수라
온도 변화가 잡음에 묻혔던 것.

조치: `sf_bake_anim.py` 에서 `flow_anim` 기본 **꺼짐** (`data/_anim.json` 으로만 켬).
실시간 재생(시퀀서·PIE)에서는 그대로 켜져 있어도 무방하다.

### (2) A/B/C/D 깜빡이는 라이팅 → 중립 마커 + 그래프

빨강/파랑 점멸 라이트를 제거하고 두 가지로 대체:

- 레벨: `sf_geom.build_markers(neutral=True)` — **중립 회색** 위치 기둥+구.
  색을 빼서 온도 컬러맵과 오독될 여지를 없앴다.
- 영상: `src/make_video.py draw_probe_chart()` — 우상단에 **A/B/C/D 온도 시계열
  그래프 + 현재 시각 커서 + 값 라벨** (`data/probes.csv` 기반). 점의 색이 아니라
  숫자와 곡선으로 말한다.

### (3) 공간이 더 읽히게 — 수직 단면 + 방 윤곽

- `SF_VSlice` — 에어컨을 지나는 **y=2.0 m 수직 온도 단면** (`src/make_slice.py` →
  `data/slices/vslice_NN.csv`). 수평 단면 하나로는 한 높이만 보인다. 이 면이 있어야
  찬 공기가 내려오고 더운 공기가 천장에 남는 **성층**과 하강 제트가 보인다.
- `SF_Outline` — 방 윤곽선(바닥·천장 테두리). 바닥을 어둡게 했더니 공간 형태가
  안 읽혀서 추가.
