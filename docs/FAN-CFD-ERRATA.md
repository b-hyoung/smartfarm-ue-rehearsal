# 팬 CFD 오류 기록

해석을 돌리는 과정에서 나온 오류를 하나씩 남긴다. 증상, 원인, 증거, 고친 방법,
확인한 방법, 영향 범위를 같은 순서로 적는다.

---

## E-001 · 팬 셀 영역이 비어 팬이 계산에 전혀 들어가지 않음

- 발견: 2026-09-21, 케이스 1번(01_R0) 실행 중
- 심각도: 치명. 고치지 않으면 3번 이후 모든 케이스가 "팬 없는 해석"이 된다.
- 상태: 고침

### 증상

팬을 켠 케이스인데도 운동량 소스가 아무 일도 하지 않는다. 실행 자체는 정상 종료하므로
로그만 봐서는 드러나지 않는다.

### 원인

격자 한 변이 0.10 m 균일인데, 팬 셀 영역 상자의 두께를 실제 팬 두께인 0.08 m 로 잡았다.
`topoSet` 의 `boxToCell` 은 **셀 중심**이 상자 안에 있는 셀만 고른다. 한 변보다 얇은
상자는 정렬에 따라 한 개도 못 잡는다.

이번 배치가 정확히 그 경우였다. 내부 블록은 x 가 −1.8 m 에서 1.8 m 까지 36 등분이라
셀 중심이 −1.45, −1.35, −1.25, −1.15 … 에 놓인다. 팬 상자는 −1.34 ~ −1.26 이었다.
두 중심 사이에 상자가 통째로 끼어 **선택된 셀 0 개**가 된다.

`vectorSemiImplicitSource` 는 빈 `cellZone` 을 오류로 보지 않는다. 그래서 solver 는
경고 없이 끝까지 돌고, 결과만 팬이 없는 것과 같아진다.

### 증거

```
x 셀 중심 : ... -1.45  -1.35  -1.25  -1.15 ...
팬 상자    :              -1.34 ~ -1.26        <- 중심이 하나도 없음
```

### 고친 방법

`src/fan_bc.py` 에 `zone_box()` 를 새로 두었다. 셀 영역 상자는 축마다 격자 한 변의
1.2 배 아래로 줄어들지 않게 키운다. 어디에 놓든 축마다 최소 한 줄은 들어온다.

실제 팬 치수는 `fan_box_cfd_m` 으로 따로 남겨 둔다. 셀 영역만 격자에 맞춰 키운 것이다.

총 추력은 변하지 않는다. `volumeMode absolute` 라 추력을 N 단위로 그대로 주고,
solver 가 영역 부피로 나눠 쓴다. 상자가 커져도 팬이 방에 넣는 운동량의 합은 같다.

### 확인한 방법

3번 케이스를 따로 복사해 격자부터 `topoSet` 까지 다시 돌렸다.

```
Adding cells with centre within boxes 1((-1.36 1.9 0.63) (-1.24 2.1 0.83))
cellZoneSet fan_t0_s0 now size 8
```

팬 하나에 8 셀(2×2×2)이 잡힌다. 고치기 전에는 0 이었다.

### 다시 나지 않게 한 조치

`Allrun` 에 검사를 넣었다. 팬 `topoSet` 뒤에 빈 영역이 하나라도 있으면 그 자리에서
멈춘다.

```bash
if grep -q 'cellZoneSet .* now size 0' log.topoSet; then
    echo '팬 셀 영역이 비었다. 상자가 격자(0.10 m)보다 얇다.'
    exit 1
fi
```

### 영향 범위

- 1번(R0), 2번(R1) : 영향 없음. 둘 다 팬을 켜지 않는 기준선이다.
- 3번 이후 : 영향 있음. 다만 아직 한 건도 시작하지 않았으므로 버린 계산은 없다.
- 이미 돌던 1번은 60 초 저장본에서 이어받았다.

### 남은 숙제

이 오류는 격자가 거칠어서 드러난 것이다. 격자 0.10 m 자체에 논문 근거가 없고 격자
수렴도 확인한 적이 없다. 할 일은 `docs/FAN-CFD-METHOD.md` 5절에 적어 두었다.

## E-002 · 판정면이 재배 베드가 아니라 방 전체 단면이었다

- 발견: 2026-09-23, 1~10 번을 채점하다가
- 심각도: 치명. **여태 낸 순위와 결론이 전부 이 값 위에 서 있었다.**
- 상태: 고침 (채점 쪽만. 계산은 다시 돌리지 않았다)

### 증상

캐노피 풍속이 터무니없이 낮게 나왔다. 팬 네 대를 6.0 CMM 으로 돌려도 P10 이
0.071 m/s 로, 목표 0.3 의 4 분의 1 이었다. "풍량으로는 안 된다", "전부 하한 미달",
"바람이 캐노피를 안 지난다" 같은 결론이 여기서 나왔다.

### 원인

`controlDict` 의 `surfaces` 함수오브젝트가 평면을 이렇게 정의한다.

```
type        plane;
pointAndNormal { point (0 2.0 0.675); normal (0 0 1); }
```

**평면 하나를 정의했을 뿐 범위를 자르지 않았다.** OpenFOAM 은 그 평면이 격자를 가르는
**전체**를 찍는다. 곧 재배 베드 위(x ±1.2, y 1.6~2.4)가 아니라 **방 전체 단면**
(x −4~4, y 0~5.7)이 나온다.

`data/fan_params.json` 의 `judge_planes` 에는 `x_range_cfd_m`·`y_range_m`·`n_points 4961`
이 적혀 있다. 만들어만 놓고 **딕셔너리로 넘기지 않았다.**

### 증거

5 번 케이스 600 초 표본 한 장을 좌표로 세어 보면 이렇다.

```
전체 점       5,124
베드 안       855   (16.7 %)
x 범위 −4.00 ~ 4.00   y 범위 0.00 ~ 5.70
```

**83 % 가 상추가 없는 방 구석이다.** 거기는 바람이 거의 없으니 P10 이 그 값을 읽는다.

같은 파일을 범위만 갈라 채점하면 이렇게 갈린다.

| 케이스 | 범위 | P10 | P50 | P90 |
|---|---|---|---|---|
| 05 F3 | 방 전체 | 0.071 | 0.193 | 0.714 |
| 05 F3 | **베드만** | **0.330** | 0.610 | 1.339 |
| 06 F4 | 방 전체 | 0.061 | 0.257 | 0.903 |
| 06 F4 | **베드만** | **0.458** | 0.786 | 1.622 |

### 고친 방법

`src/judge.py` 의 `read_points()` 에 `crop=(x0, x1, y0, y1)` 을 붙이고,
`judge_crops()` 가 `fan_params.json` 의 `judge_planes` 에서 면마다 범위를 읽어 넘긴다.
`--no-crop` 으로 옛 방식과 대조할 수 있다.

**계산은 다시 돌리지 않았다.** `raw` 파일에 점마다 좌표가 들어 있어 읽을 때 거르면 된다.

### CFD 쪽을 왜 안 고쳤나

`surfaces` 에 범위를 넣어 애초에 베드만 찍게 할 수도 있었지만 그렇게 하지 않았다.

- 방 전체를 찍어 두면 **바람이 어디로 새는지** 나중에 볼 수 있다.
- 5,124 점이라 용량이 작다.
- 돌고 있는 케이스와 형식이 달라지면 섞인다.

**원본은 넓게, 해석은 좁게.** 범위를 좁히는 것은 채점할 때 한다.

### 확인한 방법

`--no-crop` 과 기본값을 같은 데이터에 돌려 두 표를 나란히 놓고 봤다.
점 수가 5,124 에서 829~855 로 줄고, 베드 밖 점이 전부 빠졌다.

### 영향 범위

**2026-09-23 이전에 이 저장소와 문서에 적힌 캐노피 풍속 값은 전부 방 전체 단면 값이다.**
다시 채점해야 한다. 특히 다음 결론들이 뒤집혔다.

| 옛 결론 | 다시 본 결과 |
|---|---|
| "전부 하한 미달, 1 등이 목표의 4 분의 1" | 1 등 P10 0.227 로 **목표의 4 분의 3** |
| "바람이 모자라다" | **과한 자리가 문제다.** 05·06 의 P90 이 1.34·1.60 으로 상한 1.0 초과 |
| "풍량을 올려야 한다" | 풍량을 올리면 부족이 줄어든 만큼 **과함이 늘어난다**(03 부족 23 %·과함 6 % → 06 부족 6 %·과함 30 %) |
| 층간 차이 0.05 로 작다 | 베드만 보면 **0.14 ~ 0.59** 로 훨씬 크다 |

### 남은 숙제

`judge_planes` 의 `sample_grid`(121 × 41)와 `n_points`(4,961)도 쓰이지 않는다.
실제로 잘라 보면 베드 안 점이 829~855 개다. 격자가 0.05 m 라 2 cm 간격 설계와 다르다.
이 값들을 실제와 맞추거나, 쓰지 않는다는 것을 항목에 적어야 한다.

## E-003 · 에어컨 위치 케이스(G7, 25~30)가 전부 기준 위치로 돌아가고, 옮긴 위치에서는 취출면이 비었다

- 발견: 2026-09-22, 윈도우 PC 에서 25~30 번 격자를 만들면서
- 심각도: 치명. 고치지 않으면 25~29 번은 5 번(F3)과 같은 계산이 되고, 30 번은 2 번(R1)과 같아진다.
- 상태: 고침 (윈도우 PC 의 25~30 번 결과에 반영됨)

### 증상 둘

1. 생성기가 에어컨 취출·리턴 `topoSetDict` 를 **템플릿에서 그대로 복사**했다. `fan_params.json` 의
   `cases[].ac.topoSet_boxes_cfd_m` 에 옮긴 좌표가 있는데 쓰지 않았다. G7 케이스 여섯이 전부
   기준 위치 (4.0, 2.0) 에어컨으로 돌 판이었다.
2. 좌표를 쓰게 고친 뒤에도 옮긴 위치에서는 취출면이 제대로 안 잡혔다. 25_A1 은 6·3·5·5 장,
   27_A3 과 30_A6 은 3·3·**0**·6 장(기준 위치는 6·6·6·6, 리턴 36). 0 장이면 그 슬롯의 급기가
   통째로 사라진다. `flowRateInletVelocity` 는 면 수와 무관하게 풍량을 맞추지만 면이 없으면
   맞출 곳이 없다.

### 원인

- 1 은 생성기 누락.
- 2 는 격자 구조. 템플릿 blockMesh 는 안쪽 블록(x ±1.8, y 0~2.9)만 직교 0.1 m 이고 바깥 세 블록은
  반타원을 따라 비스듬하다. 기준 위치의 취출 상자(폭 0.06 m)는 안쪽 블록의 면 중심에 맞춰
  잡혀 있어 정확히 6 장이 들어오지만, 에어컨을 A1(2.0,1.5)·A2(6.0,3.5)·A3(4.0,3.5)·A5(6.0,1.2)
  로 옮기면 상자가 바깥 블록에 걸려 면 중심이 상자 안에 없거나 들쭉날쭉 들어온다. A4(2.5,2.0)
  만 안쪽 블록에 남아 정상이었다.

### 증거 (25_A1 격자, 상자 두께별 취출면 수)

```
case    thick   inletXp inletXm inletYp inletYm return
27_A3   0.06    3       3       0       6       22
27_A3   0.10    5       5       2       6       22
27_A3   0.12    6       6       6       6       22
25_A1   0.06    6       3       5       5       36
25_A1   0.10    6       6       7       7       36
```

두께 하나로는 여섯 케이스가 다 안 맞는다.

### 고친 방법

1. `make_foam_cases.py` 에 `topo_ac()` 를 넣어 케이스에 `ac.topoSet_boxes_cfd_m` 이 있으면 그것으로
   `topoSetDict.ac` 를 쓴다. 없으면 예전처럼 템플릿을 복사한다.
2. `src/ac_snap.py` 가 격자 위에서 슬롯마다 두께 후보(0.06~0.18 m)와 리턴 배율 후보(1.0~1.5)를
   `topoSet` 으로 세어 보고, 면 수가 목표(취출 6, 리턴 36)에 가장 가까운 상자(같으면 작은 것)를
   골라 각 케이스의 `system/topoSetDict.ac` 를 다시 쓴다. 고른 상자는 `case.json` 의
   `ac_boxes_snapped` 와 `cases/fan-study/ac_boxes_snapped.json` 에 남는다.

   ```
   python3 src/make_foam_cases.py --cases 25-30 ...     # 먼저 케이스를 만들고
   python3 src/ac_snap.py                                # 격자에 맞춰 취출 상자를 고른다 (한 케이스 격자를 빌려 topoSet 만 돈다)
   ```

### 확인한 방법

다시 쓴 `topoSetDict.ac` 로 같은 격자에서 면 수를 다시 셌다.

```
25_A1  6 6 6 6  36
26_A2  5 5 6 6  37
27_A3  6 6 6 6  36
28_A4  6 6 6 6  36
29_A5  5 6 6 6  33
30_A6  6 6 6 6  36
```

26 과 29 는 한 면씩 ±1 장(면적 17 %)이 남는다. 풍량은 같고 토출 속도만 그만큼 달라진다.
0 장은 없다.

### 영향 범위

- 25~30 번(윈도우 PC): 고친 상태로 돌렸다. 다른 컴퓨터에서 G7 을 다시 만들 때는 반드시
  `ac_snap.py` 까지 돌려야 한다.
- 1~24 번: 에어컨이 기준 위치라 영향 없다.

### 남은 숙제

옮긴 위치의 취출 형상은 격자에 맞춘 근사다. 에어컨 위치가 판정에 크게 작용한다고 나오면,
바깥 블록도 직교로 다시 짜거나 취출구를 blockMesh 패치로 직접 새기는 편이 맞다.

## E-004 · 에어컨 취출이 실물 4Way 베인 25° 가 아니라 수직 아래다 (템플릿 이름이 오해를 부른다)

**2026-09-24 확인. 30 케이스 전부 해당. 계산을 다시 돌려야 하는 오류는 아니지만,
"베인 각도까지 넣고 돌렸다" 고 읽히면 안 된다.**

### 무엇이 틀렸나

팬 스터디가 쓰는 템플릿 폴더 이름은 `cfd/template/acRoom-vane25` 다. 이름만 보면
실물 취출각(4방향 25°)이 들어간 것 같지만, **그 안의 경계조건은 수직 아래다.**

```
cfd/template/acRoom-vane25/0.orig/U
  inletXp { type flowRateInletVelocity; volumetricFlowRate constant 0.104167;
            value uniform (0 0 -3.47); }        // 네 슬롯 모두 같다
```

`flowRateInletVelocity` 는 **패치 법선 방향으로만** 분다. 그리고 취출면은 천장의
수평 띠다(`system/topoSetDict`, 예: `box (0.397 1.675 2.699) (0.457 2.325 2.701)` —
z 두께 0.002 m). 법선이 곧 아래라, 각도가 들어갈 자리가 없다.

`data/ac_params.json` 은 이미 이렇게 적어 두고 있었다.

```
"direction": "patch normal (수직 아래) — ⚠ 실물 베인은 바깥으로 뿜음.
              베인 각도 실측 후 (cos, 0, -sin) 으로 교체 필요"
```

### 왜 중요한가 — 앞선 계산에서 이미 크게 달랐다

`docs/OBJECTIVES.md` 13 절(2026-09-10, 재배단 없는 방)에서 수직 취출과 vane25 를
견줬을 때 방의 기류 구조 자체가 뒤집혔다.

| | 수직 취출 | vane25 |
|---|---|---|
| t=60 s 방 평균 | 27.66 ℃ | 26.2 ℃ |
| 기류 구조 | 가운데 한 줄기 하강 | 4방향 천장 제트 → 방 중간 cold dump |
| 에어컨 바로 아래(A) | 강한 하강 제트 | **상승 0.16 m/s** (리턴 흡입) |

**재배단은 카세트 바로 아래에 있다**(둘 다 UE (4.0, 2.0)). 즉 가장 많이 달라지는
자리에 재배단이 놓여 있다. 그 절의 "1. ~~취출 방향 수직~~ → 해결(vane25)" 은
**그때 그 계산에 대한 말이고, 팬 스터디에는 물려받지 못했다.**

### 판정이 뒤집힐 위험은 얼마나 되나

지금 격자에서 에어컨만 켠 케이스는 캐노피에 거의 아무것도 못 준다.

| 케이스 | 조건 | P10 | P50 | P90 |
|---|---|---|---|---|
| 01_R0 | 재배단 없음, 팬 없음 | 0.072 | 0.102 | 0.663 |
| 02_R1 | 재배단, 팬 끔 | 0.059 | 0.136 | **0.206** |
| 30_A6 | 재배단, 팬 끔, 에어컨 이동 | 0.061 | 0.094 | 0.112 |
| 05_F3 | 재배단, 팬 4 대 6 CMM | 0.316 | 0.614 | **1.333** |

팬을 켜면 P90 이 **6.5 배**다. 캐노피 풍속은 사실상 팬이 만든다.

- **풍량·대수·각도·높이 비교(1 ~ 24 번)** — 모든 케이스가 같은 에어컨 경계를 쓰는
  통제 비교이고 에어컨 몫이 작다. 순위가 뒤집힐 가능성은 낮다.
- **에어컨 위치 비교(G7, 25 ~ 30 번)** — 이 여섯은 **에어컨 자체를 묻는 케이스다.**
  25 ~ 29 의 P10 이 0.363 ~ 0.418 로 서로 붙어 있는 것(“위치는 별 영향 없다”)이
  취출 방향을 틀리게 준 탓일 수 있다. **이 결론은 보류한다.**
- 방 규모 재순환이 달라지면 팬 제트가 뿜어지는 배경이 달라져 P90 꼬리가 움직일 수 있다.
  크기는 모른다.

### 고치려면 — 단순히 방향만 바꾸면 안 된다

`fixedValue` 로 25° 방향을 주되, **면적을 같이 키워야 한다.**

슬롯 하나의 면적은 0.030 m² 다(`slot_area_m2_assumed` 0.12 m² ÷ 4 슬롯, 격자에서
고른 면적과도 맞는다). 지금 수직 취출 속도는 0.104167 / 0.030 = **3.47 m/s** 로
카세트로서 그럴듯한 값이다.

방향만 25° 로 눕히고 면적을 그대로 두면, 법선 성분으로 같은 풍량을 내기 위해
|U| = 3.47 / sin 25° = **8.2 m/s** 가 된다 — 카세트가 낼 수 없는 속도고, 천장 제트
운동량을 2.37 배로 부풀린다. 질량과 운동량을 같이 맞추려면 취출면을 1/sin 25° =
2.37 배(슬롯당 0.071 m²)로 넓혀 |U| = 3.47 m/s, 법선 성분 1.47 m/s 로 두어야 한다.
즉 `topoSetDict` 의 취출 상자부터 다시 잡아야 하는 일이다.

### 지금 상태

- **고치지 않았다.** 돌아간 30 케이스는 전부 수직 취출이다.
- 미리보기 웹(`web/fan-wind.html`)과 3D 설명에는 이 한계가 적혀 있다.
- 템플릿 이름 `acRoom-vane25` 는 내용과 맞지 않는다. 바꾸면 다른 컴퓨터의 경로가
  깨지므로, 이름은 두고 이 항목으로 경고를 대신한다.

## E-005 · 에어컨 취출면이 격자보다 좁아 2 배로 잡혔다 — 취출 속도가 절반이다

**2026-09-24 확인. 30 케이스 전부 해당. E-001 과 같은 뿌리인데 에어컨에는 고치지 못했다.**

### 무엇이 틀렸나

슬롯 하나의 면적을 실제로 재 봤다(`surfaceFieldValue`, `areaNormalIntegrate`, 05_F3 600 초).

```
inletXp   Faces: 6   Area: 6.000000e-02   areaNormalIntegrate(U) = -0.104167
```

**풍량은 정확하다**(0.104167 m³/s = 6.25 CMM). 면적이 틀렸다.

| | 면적 m² | 취출 속도 m/s |
|---|---|---|
| 실물 가정 (`ac_params.json` `slot_area_m2_assumed` 0.12 ÷ 4 슬롯) | 0.030 | 3.47 |
| `topoSetDict` 상자가 노린 값 (0.06 × 0.65) | 0.039 | 2.67 |
| **격자에서 실제로 잡힌 면** | **0.060** | **1.74** |

`0.orig/U` 의 `value uniform (0 0 -3.47)` 은 초기 추정값일 뿐이다.
`flowRateInletVelocity` 는 실제 패치 면적으로 속도를 다시 계산하므로, 돌아간 값은 **1.74 m/s** 다.

### 왜 이렇게 됐나

슬롯 폭이 0.06 m 인데 천장 격자가 0.10 m 다. `boxToFace` 는 면을 통째로만 고를 수 있어
0.10 m 폭 면을 집었다 — **E-001(팬 상자 0.08 m < 격자 0.10 m)과 똑같은 오류다.**

E-001 은 팬·재배단 둘레를 0.05 m 로 세분해서 고쳤다. 그런데 세분 상자가
`(-1.8, 1.2, 0.0) ~ (1.8, 2.8, 2.4)` 라 **z 2.4 m 에서 끝난다.** 에어컨은 z 2.7 m 라
그 수정이 닿지 않았다.

### 영향

질량은 맞고 **운동량이 절반**이다(운동량 ∝ ρ Q U). 천장 제트가 실제보다 약하게 퍼진다.
E-004(방향이 수직)와 **겹쳐서** 들어가 있다 — 방향도 틀리고 세기도 절반이다.

### 고치려면

세분 상자를 천장까지 올리거나(`fan_bc.py` 의 `refine_box()` z 상한 2.4 → 2.7),
취출구를 `blockMesh` 패치로 직접 새긴다. E-004 의 면적 보정(2.37 배 확대)과 **같이**
풀어야 한다 — 따로 고치면 서로 어긋난다.

## E-006 · 재배단 선반이 방 외벽의 29 ℃ 고정을 물려받아 캐노피에 278 W 를 넣는다

**2026-09-24 확인. 재배단이 있는 29 케이스(01_R0 제외) 해당.**

### 무엇이 틀렸나

`src/make_foam_cases.py` 의 `add_rack_patch()` 는 **`walls` 블록을 그대로 복사해서**
`rackWalls` 를 만든다.

```python
def add_rack_patch(field_path):
    """0.orig 각 필드에 walls 블록을 복사해 rackWalls 를 넣는다."""
```

그래서 `0/T` 가 이렇게 된다.

```
walls     { type fixedValue; value $internalField; }   // 302 K = 28.85 ℃
rackWalls { type fixedValue; value $internalField; }   // 302 K — 복사된 것
```

방 외벽을 29 ℃ 로 고정하는 건 바깥 열이 들어온다는 **의도된 가정**이다
(`docs/OBJECTIVES.md` "벽 29 ℃ 고정"). 그런데 재배단 선반은 **냉방되는 방 안**에 있다.
공기와 함께 식어야 하는데 영원히 28.85 ℃ 로 붙들려 있다.

### 얼마나 들어가나

`buoyantPimpleFoam -postProcess -func wallHeatFlux` (05_F3, 600 초):

```
integ(walls)     = 1458.5 W
integ(rackWalls) =  278.3 W
```

**선반이 278 W 를 캐노피 바로 아래에서 넣고 있다.** 우리는 조명 발열 480 W 를
일부러 뺐는데(`fan_params.json` `lighting.included: false`), 그 **58 %** 가 의도치 않게
다시 들어간 셈이다. `fan_params.json` 의 `heat_sources` 는 `[]` 인데 실제 계산에는
합계 1.74 kW 가 들어가 있다.

### 영향

부력을 통해 기류에 작용한다. 선반 바로 위가 캐노피라 **가장 예민한 자리**다.
풍속 순위에 얼마나 작용하는지는 재 보지 않았다.

### 고치려면

`rackWalls` 의 T 를 `zeroGradient`(단열)로 두는 것이 기본값으로 맞다. `walls` 만
`fixedValue` 로 남긴다. `add_rack_patch()` 가 T 필드만 다르게 쓰도록 고쳐야 한다.
